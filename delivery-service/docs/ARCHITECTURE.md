# Архитектура системы

## Обзор

Система "Сервис доставки еды" состоит из трех основных компонентов:

1. **Backend (REST API)** - Серверная часть с бизнес-логикой
2. **Mobile App** - Мобильное приложение для курьеров
3. **Web Client** - Веб-интерфейс для клиентов

## Архитектурная диаграмма

```

│  Mobile App     │         │   Web Client    │
```

## Backend архитектура

### Трехслойная архитектура

```
┌─────────────────────────────────────┐
│   Routes Layer (Маршруты)           │
│   - Определение endpoints           │
│   - Маршрутизация запросов          │
└─────────────┬───────────────────────┘
              │
┌─────────────▼───────────────────────┐
│   Controller Layer (Контроллеры)    │
│   - Обработка HTTP запросов         │
│   - Валидация входных данных        │
│   - Формирование ответов            │
└─────────────┬───────────────────────┘
              │
┌─────────────▼───────────────────────┐
│   Model Layer (Модели)              │
│   - Бизнес-логика                   │
│   - Работа с БД                     │
│   - Валидация данных                │
└─────────────────────────────────────┘
```

### Middleware компоненты

```
Request → [Auth] → [Validation] → [Controller] → [ErrorHandler] → Response
```

1. **Authentication Middleware**
   - Проверка JWT токена
   - Извлечение данных пользователя
   - Проверка прав доступа

2. **Validation Middleware**
   - Валидация входных данных
   - Проверка форматов
   - Санитизация данных

3. **Error Handler**
   - Централизованная обработка ошибок
   - Логирование
   - Формирование ответа об ошибке

## Потоки данных

### 1. Создание и назначение заказа

```
1. Администратор создает заказ (Web/API)
2. Backend сохраняет заказ в БД со статусом "created"
3. Администратор назначает заказ курьеру
4. Backend обновляет статус на "assigned"
5. Курьер получает уведомление (Push notification)
6. Курьер видит заказ в своем списке (Mobile App)
```

### 2. Выполнение заказа курьером

```
1. Курьер открывает детали заказа (Mobile App)
2. Курьер нажимает "Принять" → статус "in_progress"
3. Mobile App начинает отправлять геолокацию
4. Backend сохраняет координаты в БД
5. Клиент видит обновление на карте (Web Client)
6. Курьер доставляет заказ
7. Курьер нажимает "Доставлен" → статус "delivered"
8. Клиент видит финальный статус
```

### 3. Отслеживание заказа клиентом

```
1. Клиент вводит номер заказа (Web Client)
2. Web Client запрашивает данные через API
3. Backend возвращает информацию о заказе и последнюю геолокацию
4. Web Client отображает карту с маркерами
5. Web Client запрашает обновления каждые 5-10 секунд (polling)
6. При изменении данных карта обновляется
```

## Безопасность

### Уровни защиты

1. **Transport Layer**
   - HTTPS для всех соединений
   - TLS 1.2+

2. **Authentication**
   - JWT токены
   - Безопасное хранение токенов
   - Автоматическое обновление токенов

3. **Authorization**
   - Role-based access control (RBAC)
   - Курьеры видят только свои заказы
   - Клиенты видят только свои заказы

4. **Data Layer**
   - Параметризованные запросы (защита от SQL injection)
   - Валидация и санитизация входных данных
   - Хеширование паролей (bcrypt)

5. **API Layer**
   - Rate limiting
   - CORS настройки
   - Input validation

## Эмуляция геолокации

### Алгоритм эмуляции

```
1. При изменении статуса на "in_progress":
   - Получить координаты ресторана (start)
   - Получить координаты доставки (end)

2. Генерация маршрута:
   - Разбить маршрут на N точек (например, 10-20)
   - Рассчитать координаты промежуточных точек
   - Добавить небольшую случайность для реалистичности

3. Отправка координат:
   - Каждые 10 секунд отправлять следующую точку
   - Сохранять в БД с меткой времени

4. При достижении конечной точки:
   - Прекратить отправку
   - Ждать подтверждения доставки от курьера
```

## Масштабируемость

### Горизонтальное масштабирование

1. **Backend**
   - Развертывание нескольких инстансов за Load Balancer
   - Stateless API (состояние в токенах)

2. **Database**
   - Master-Slave репликация для чтения
   - Индексирование часто используемых полей
   - Connection pooling

3. **Кеширование**
   - Redis для сессий и часто запрашиваемых данных
   - Кеширование списка активных заказов

## Мониторинг и логирование

1. **Логирование**
   - Все API запросы
   - Ошибки и исключения
   - Изменения статусов заказов
   - Действия пользователей

2. **Метрики**
   - Время отклика API
   - Количество активных пользователей
   - Количество заказов по статусам
   - Нагрузка на сервер
